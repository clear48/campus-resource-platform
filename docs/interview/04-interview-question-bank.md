## 2. 项目背景与总体设计

### Q1：这个项目解决什么问题？

回答抓手：

- 校园资料分散、重复、质量不可控、结构化检索弱、下载容易滥用；
- 平台建立“文件上传—资料提交—管理员审核—公开搜索/下载/收藏—排行榜”的闭环；
- MySQL 保存权威业务，Redis 处理短期状态、缓存、实时排行和高频写聚合。

不要只回答“学生可以上传下载资料”，那会把项目说成文件表 CRUD。

### Q2：这个项目是实际有用，还是编程练习？

推荐回答：

> 它目前是面向实习面试的可运行作品集工程，不是已经有校园生产流量的商业系统。但业务问题来自真实校园资料流转，我没有只搭空架构：代码中已经落地审核状态机、文件去重与用户授权、下载防刷、一次性票据、Redis/MySQL 最终一致性和测试。生产流量、容量和收益数据我没有，因此不会虚构。

### Q3：为什么说它不是普通 CRUD？

回答四点即可：

1. 资料有审核状态机，不是任意修改状态；
2. 并发重复操作由唯一索引、条件更新和事务控制；
3. 文件访问有用户授权、管理员审核边界和一次性下载票据；
4. 下载计数与排行榜涉及 Redis、MySQL、后台任务和故障重试。

### Q4：项目中最难的部分是什么？

优先讲下载增量同步：

> 难点不是 `HINCRBY`，而是 MySQL 已提交、Redis 确认前宕机时如何防止重试重复累加。我把 Redis 增量隔离为 UUID 批次，在 MySQL 事务中先插入 `(batchId, resourceId)` 唯一幂等明细，再原子增加 `download_count`；提交后才从 Redis 批次删除。重试命中唯一键时校验 delta 并跳过重复累加。多实例再用 Redisson 看门狗锁互斥。

### Q5：项目如何分层？

Controller 处理 HTTP 和参数，Service 处理业务、权限、事务和降级，Mapper/XML 处理 SQL，DTO/VO/Entity 分离。拦截器统一做 JWT，定时任务只负责触发 Service，不把复杂同步逻辑写在 Task 中。

## 3. 文件与资料

### Q6：文件如何判断重复？

- 服务端计算 MD5，不直接信任前端；
- 使用 `MD5 + fileSize` 查询；
- Redis 缓存 `fileId` 只是加速；
- MySQL 唯一索引 `uk_file_md5_size` 是并发下最终兜底；
- 命中后复用物理文件，但还要建立当前用户的引用授权。

### Q7：为什么 MD5 之外还要 fileSize？

MD5 碰撞概率很低但不是不存在，文件大小提供额外判别维度，也能减少误复用。对于更高安全要求，还可以增加 SHA-256 或内容校验，但当前代码未实现。

### Q8：秒传会不会导致用户引用别人的文件？

如果只返回全局 `fileId`，确实有越权风险。项目用 `user_file_authorization(user_id, file_id)` 单独记录“当前用户已实际上传或验证过相同内容”，创建资料时同时校验文件正常和授权存在。

### Q9：文件上传为什么不把文件 IO 放在事务里？

文件读写可能很慢，放在数据库事务中会长时间占用连接和锁。当前先落盘，再用短事务写 `file_info` 和授权；数据库失败时补偿删除本次文件。它不是跨文件系统和数据库的强事务，而是短事务加补偿。

### Q10：文件类型如何校验？

当前真实实现：

- 50 MB 业务上限；
- 扩展名白名单；
- UUID 存储名；
- 存储根目录规范化和路径边界校验；
- MIME 仅记录，不做可信内容判定。

因此不能回答“已经做了扩展名、MIME、文件魔数三重校验”。后续可增加 Apache Tika/魔数、压缩包解压限制和恶意文件扫描。

### Q11：如何防止用户重复提交同一资料？

当前在创建资料前查询“同用户 + 同文件 + 活动状态”的记录并拒绝。要主动补充：

> 这个方案能处理普通重复提交，但并发下是先查后插，数据库没有活动态唯一约束，两个请求仍可能同时插入。严格幂等可增加请求幂等键，或设计能被唯一索引表达的活动态约束。

不要把文件唯一索引误当作资料提交幂等，因为一个物理文件和一条资料记录不是同一个业务实体。

## 4. 认证、权限与安全

### Q12：JWT 登录流程是什么？

登录校验账号和 BCrypt 密码，签发包含 `userId`、`role`、`jti` 的 JWT。拦截器解析 Bearer Token、验签、查 Redis 黑名单，再把用户写入 ThreadLocal，请求结束清理。

### Q13：JWT 无状态，为什么还用 Redis？

纯 JWT 在过期前无法由服务端主动撤销。项目把退出 Token 的 `jti` 放进黑名单，TTL 等于剩余有效期，实现单 Token 立即失效，同时黑名单自然过期。

### Q14：Redis 挂了，鉴权怎么办？

当前代码对所有受保护接口统一失败关闭：黑名单查询异常会让请求失败。优点是已退出 Token 不会因 Redis 故障重新有效；缺点是 Redis 成为受保护请求和退出登录的硬依赖。`/api/v1/auth/login` 是公开排除路径，登录验密与签发本身不查询 Redis，不能笼统说“登录接口依赖 Redis”。

可演进为：

- 敏感管理接口继续失败关闭；
- 明确 Redis 高可用与监控；
- 或设计用户级 Token version 等可校验状态。

不能简单“Redis 挂了就全部放行”。

### Q15：用户被禁用后，旧 JWT 会立即失效吗？

不会完全立即失效。当前大多数接口只信任 JWT 中的角色和 Redis `jti` 黑名单，没有每次回查用户状态，也没有 `token-version`。默认 Token 有效期 2 小时，旧 Token 可能继续使用到过期。

优化方向是敏感管理接口回查用户状态，或为用户维护登录态版本，在禁用/降权时整体失效。

### Q16：如何防越权？

- 当前用户 ID 只从 JWT 上下文取，不接收前端 `userId`；
- 创建资料必须有当前用户的文件授权；
- 下载记录必须属于当前用户；
- 管理员角色在 Service 校验；
- 审核文件只能通过待审核资料关系读取；
- 文件取流前复核资料仍然通过审核且 fileId 未变化。

### Q17：一次性下载票据解决什么？

只凭 `downloadRecordId` 下载会形成可猜测、可长期重放的访问入口。项目生成 32 字节随机票据，Redis Key 中只放 SHA-256 摘要，TTL 60 秒，并用 Lua 原子删除。票据还绑定用户和记录，重放、过期或换用户都失败。

## 5. MySQL 与事务

### Q18：核心表为什么这样拆？

- `file_info` 是物理文件；
- `resource` 是业务资料；
- `audit_record` 是状态变更历史；
- `favorite` 是用户和资料关系；
- `download_record` 是审计历史；
- `download_delta_sync_item` 是后台同步幂等栅栏；
- `user_file_authorization` 是跨用户文件复用的权限边界。

拆表依据是实体生命周期和一致性边界，不是为了多建表。

### Q19：项目有哪些关键索引？

优先讲：

- 文件 `(file_md5, file_size)` 唯一；
- 收藏 `(user_id, resource_id)` 唯一；
- 下载同步 `(batch_id, resource_id)` 唯一；
- 资料 `(status, created_at)`、`(category_id, status, created_at)`、`(uploader_id, status, created_at)`；
- 下载记录 `(user_id, created_at)`。

回答时把每个索引绑定到真实 SQL，不要只背“最左前缀”。

### Q20：为什么前置查重后还需要唯一索引？

两个并发请求可能同时查询到不存在，再同时插入。前置查询只是给用户友好提示，数据库唯一索引才是最终一致性防线。

### Q21：审核并发如何处理？

先查状态用于给出业务提示，真正更新时 SQL 带 `WHERE status = PENDING_REVIEW`。两个管理员同时操作时最多一个更新 1 行，另一个更新 0 行并返回状态已变化。资料更新和审核流水同事务。

### Q22：收藏数量如何避免并发错误？

- 收藏关系唯一索引；
- 收藏/取消用旧状态条件更新；
- 状态变更和 `favorite_count` 原子加减在同一事务；
- 递减 SQL 要求计数大于 0；
- Redis 缓存和热度在提交后更新。

### Q23：为什么收藏用 TransactionTemplate？

业务需要在事务提交完成后再写 Redis，同时并发插入的 `DuplicateKeyException` 要在失败事务结束后捕获并重新读取赢家记录。`TransactionTemplate.execute` 让这段“事务内数据库动作—事务外异常转换和缓存更新”的边界更直观。

### Q24：项目如何理解 Spring 事务失效？

`@Transactional` 依赖 Spring 代理；同类内部直接调用事务方法可能绕过代理。项目把下载增量持久化和热度快照写入拆到独立 Bean，由编排 Service 调用代理对象。

还要知道默认只有 RuntimeException 和 Error 回滚；项目显式使用 `rollbackFor = Exception.class`。

### Q25：SQL 如何做优化？

本项目能诚实讲的是设计和验证路径，不能虚构“从 1.2 秒降到 50 毫秒”：

1. 根据接口 SQL 确定 WHERE、ORDER BY 和分页；
2. 设计联合索引；
3. 用 `EXPLAIN` 检查访问类型、使用索引、扫描行数、额外排序；
4. 用真实数据量和慢查询日志验证；
5. 修改后对比执行计划和接口指标。

当前 `%LIKE%` 前导模糊查询是明确瓶颈，数据量增长后应评估全文索引或 Elasticsearch。

### Q26：为什么不用物理外键？

项目使用逻辑外键，由 Service 处理权限、状态、软删除和审计。优点是写入和迁移灵活，代价是绕过 Service 可能产生孤儿数据，需要完整性巡检。小型强完整性系统使用物理外键同样合理。

## 6. Redis、限流与一致性

### Q27：Redis 在项目中有哪些真实场景？

按结构回答：

- String：JWT 黑名单、MD5 三态缓存、公开详情 JSON、下载去重、一次性票据和当前同步批次指针；
- Set：用户收藏状态；
- ZSet：热门资料、热门搜索词、下载滑动窗口；
- Hash：下载量增量和同步批次；
- Lua：限流、票据消费、批次隔离和指针比较删除；
- Redisson：下载同步锁、总榜维护读写锁和公开详情每资料互斥锁。

### Q28：为什么限流用 ZSet，而不是固定窗口计数器？

固定窗口在边界处可能出现突发，例如前一分钟末尾和下一分钟开头集中通过。ZSet 把毫秒时间戳作为 score，每次删除 60 秒窗口外请求，再统计窗口内成员，更平滑。

代价是每次请求需要维护一个 member，内存和命令复杂度高于简单计数器。

### Q29：为什么用 Lua？

限流需要“清理—计数—判断—写入—过期”作为一个原子步骤；票据需要“存在则删除”原子执行。客户端多命令会产生竞态，Lua 在 Redis 服务端原子执行。

### Q30：为什么用 Redisson，不直接 SETNX？

- 看门狗自动续期，避免长任务锁提前过期；
- 锁归属校验，只有持有线程解锁；
- 支持 `RReadWriteLock`，匹配总榜重建写锁和实时增量读锁；
- 减少自研锁的续期、误删和异常释放问题。

但 Redisson 只解决互斥，不等于业务幂等；下载同步仍需要 MySQL 唯一键。

### Q31：Redis 和 MySQL 是强一致吗？

不是。按数据分类：

- 审核和收藏的权威事实在 MySQL，Redis 提交后更新，失败可回源或重建；
- 下载量先写 Redis，再以批次幂等方式最终同步 MySQL；
- 排行榜是可重建派生数据；
- JWT 黑名单和下载票据是短期安全状态，Redis 故障失败关闭。

### Q32：下载去重和计数是否原子？

当前不是完全原子。代码先 `SETNX` 十分钟去重 Key，再 `HINCRBY` 下载增量。如果第一步成功、第二步失败，会在去重期内少计一次。

优化方式是用 Lua 把“检查/写去重 Key + HINCRBY”合并为原子脚本。这是现有实现边界，不能回答成已经保证原子。

### Q33：下载量为什么不每次直接更新 MySQL？

下载量是高频热点字段，每次 `UPDATE resource SET download_count = download_count + 1` 会增加数据库写压力和热点行竞争。Redis Hash 先聚合多次事件，定时批量落库。

代价是最终一致、实现复杂、需要处理任务失败和重复执行，因此项目增加 UUID 批次、分布式锁和 MySQL 幂等明细。

### Q34：如果 MySQL 已提交，但 Redis 还没删除就宕机呢？

下次任务读取同一 UUID 批次。MySQL 插入 `(batch_id, resource_id)` 时命中唯一键，校验已保存 delta 后跳过重复累加，再次执行 Redis 确认。因此不会因为确认失败而重复增加。

### Q35：周期排行榜是真正的日榜、周榜、月榜吗？

当前不是精确自然周期榜。Key 固定为 `daily/weekly/monthly`，每次写入都会刷新 2/14/60 天 TTL；持续有流量时会持续累积。

准确表述是“不同保留期的周期标签榜”。要实现自然周期，应把日期、ISO 周、月份加入 Key，或定时原子换榜，并补跨周期测试。

### Q36：Redis 榜单有脏数据怎么办？

Redis 只存 `resourceId + score`。查询后批量访问 MySQL，固定过滤 `APPROVED`，按 Redis 原顺序组装；最多分批扫描 500 个候选补足。Redis 故障时资料榜降级 MySQL `hot_score`。

### Q37：缓存穿透、击穿、雪崩在本项目怎么回答？

需要按当前已实现能力和剩余边界回答：

- MD5 预检已有 5 分钟 `NOT_FOUND` 负缓存并使用 `SET NX`，可抑制同一 `MD5 + size` 重复穿透；随机高基数组合仍会产生首次查库和负缓存 Key，负缓存不能替代限流；
- 收藏空集合不建占位 Key，零收藏用户会重复回查 MySQL；
- 公开资料详情已使用 30～35 分钟 TTL 抖动、每资料 Redisson 锁和持锁后二次检查缓解雪崩与热点击穿；不存在或不可见资料不做负缓存，随机不存在 ID 仍会穿透；
- 详情缓存的 Redis/锁异常或锁等待超时路径会回源且不在锁外回填，审核提交后同锁失效；删除失败仍依赖 TTL 兜底；
- 周期榜 TTL 每次刷新，并没有大量同刻过期的问题设计证据。

后续可考虑预检限流、详情负缓存以及热点逻辑过期，但必须标为尚未实现。

## 7. Spring Boot 与 MyBatis

### Q38：为什么不用 MyBatis-Plus？

当前实际使用原生 MyBatis 3。复杂搜索、状态条件更新、原子计数、游标扫描和批量候选查询都需要可控 SQL，XML 更直观。MyBatis-Plus 可以减少简单 CRUD 样板，但不是当前技术栈，不能说已经使用。

### Q39：`#{}` 和 `${}` 有什么区别？

`#{}` 生成 PreparedStatement 参数占位，通常用于安全绑定值；`${}` 是原样字符串替换，可能带来注入风险。

项目排序列没有直接用 `${sortBy}`，而是 Service 白名单加 XML `<choose>` 输出固定列名。

### Q40：项目如何做参数校验？

DTO 使用 Jakarta Validation，Service 对关键文本、ID、分页、状态和排序再兜底校验。这样 Controller 请求能快速失败，也防止未来内部调用绕过 Controller 时写入脏数据。

## 9. 回答自检

每个回答结束前检查：

- 是否先讲业务问题；
- 是否说了真实类、表、Key 或 SQL；
- 是否说明并发/异常；
- 是否区分权威数据和派生数据；
- 是否说明代价；
- 是否把“后续优化”误说成“已实现”；
- 是否使用了没有证据的 QPS、用户量或性能百分比。
