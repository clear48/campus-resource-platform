# 项目局限与演进路线

## 1. 为什么要单独讲局限

面试中能区分“已实现、设计中、未实现”比堆砌技术名词更重要。局限不等于项目失败，它说明当前方案服务的规模、风险和成本边界。

本文件只规划后续方向，不代表已经实现。

## 2. 能力边界总表

| 主题 | 当前已实现 | 尚未实现或不完整 |
| --- | --- | --- |
| 检索 | MySQL 多字段模糊搜索、结构化筛选、排序白名单、热词统计 | 分词、全文索引、Elasticsearch、语义检索、搜索建议 |
| 文件 | 大小/扩展名白名单、MD5+size 去重、UUID 存储、路径边界、用户授权 | MIME/魔数可信校验、杀毒、压缩包安全扫描、对象存储 |
| JWT | 验签、过期、jti 黑名单、角色 Claims、ThreadLocal 清理 | Refresh Token、用户 Token version、禁用/降权后全局即时失效 |
| 下载 | 用户/IP 限流、记录、60 秒一次性票据、归属与状态复核 | 传输完成后再记成功、断点续传、可信代理头配置 |

| 测试 | 单元、Controller、MyBatis/H2/MySQL 部分集成 | Testcontainers Redis/MySQL、故障注入、并发/跨周期/压测 |

## 3. 高优先级正确性与安全问题

### 3.1 用户被禁用或降权后，旧 JWT 仍可能有效

现状：

- 拦截器验签后直接信任 JWT 中的 `role`；
- 大多数接口不回查 `user.status` 和当前角色；
- 默认 Token 有效期 7200 秒。

影响：

- 管理员被降权后，旧 Token 在过期前仍可能审核、下架或重建榜单；
- 用户被禁用后，旧 Token 仍可能访问普通受保护接口。

建议：

1. 管理员高风险操作回查当前用户状态和角色；
2. 增加 `token-version`，JWT 携带版本，禁用、改权或改密时递增；
3. 补“禁用后旧 Token”和“降权后旧 Token”HTTP 测试。

面试口径：

> 当前支持单 Token 退出黑名单，不支持用户级全部 Token 立即失效，这是认证模块最优先的演进项。

### 3.2 Redis 是所有受保护接口的鉴权硬依赖

现状：JWT 拦截器每次查询 Redis 黑名单，异常没有回源，受保护请求失败。

不能简单改成 Redis 异常全部放行，因为已退出 Token 会重新有效。

建议：

- 明确 Redis 高可用、超时和告警；
- 管理接口坚持失败关闭；
- 对普通接口是否分级降级，需要结合 Token version、风险等级和业务可用性重新设计。

### 3.3 下载计数发生在文件真正传输前

现状：

- 第一步创建下载记录时就写 `download_status = SUCCESS`；
- 同时签发票据、增加下载量和热度；
- 第二步才真正读取文件。

如果用户不发第二步请求、票据过期、文件读取失败或资料刚好下架，统计仍可能增加。

建议：

- 下载记录增加 `PENDING/SUCCESS/FAILED`；
- 第一步写 `PENDING`；
- 取流校验成功后再更新状态和计数；
- 对“字节是否完整传完”要结合 Web 服务器响应生命周期设计，不能简单在 Controller 返回流时认定完成。

### 3.4 客户端可伪造转发头绕过 IP 限流

现状：下载 Controller 读取 `X-Forwarded-For`。如果应用直连公网或网关没有清洗头部，客户端可以伪造 IP。

建议：

- 仅信任已配置的反向代理；
- 由网关覆盖外部转发头；
- 直连场景使用 `remoteAddr`；
- 保留用户维度限流作为第二道防线。

### 3.5 生产 Web 安全配置需要收敛

现状：

- CORS 使用任意 Origin Pattern，并允许携带凭证，适合本地联调但不适合直接作为生产配置；
- `ApiResponse` 虽包含 `traceId`，但当前是响应级随机值，没有接入 MDC、日志和跨服务链路。

建议：

- 按环境配置允许的前端域名、方法和请求头；
- 增加安全响应头与反向代理边界检查；
- 在请求入口生成或接收可信 traceId，写入 MDC，并在响应与日志中使用同一个值。

## 4. 并发与一致性改进

### 4.1 下载去重和增量计数原子化

现状：

```text
SETNX 去重 Key 成功
→ HINCRBY 下载增量
```

若第二步失败，十分钟内会少计一次。

建议用 Lua：

```text
如果去重 Key 已存在：返回未计数
否则：
  SET 去重 Key EX 600
  HINCRBY 增量 Hash
  返回已计数
```

两步在 Redis 内原子执行，并补异常和并发测试。

### 4.2 资料重复提交增加真正幂等

现状：同用户同文件活动资料使用“先查后插”，并发下可能插入两条待审核记录。

可选方案：

- 前端生成请求幂等 Key，服务端唯一存储；
- 引入可由唯一索引表达的活动态标识；
- 锁定稳定父记录后执行检查和插入。

选择方案前需定义“拒绝/下架后是否允许同一文件重新提交”，否则唯一约束无法准确表达业务。

### 4.3 修正 `ref_count` 语义

现状：内容去重时先 `ref_count + 1`，再 `INSERT IGNORE` 用户授权。同一用户重复上传相同内容可能反复加数；它也不等于真实资料引用数。

建议先定义字段语义：

- 若表示“获得授权的用户数”，仅用户授权首次插入成功才递增；
- 若表示“引用该文件的资料数”，应在资料创建/删除事务中增减；
- 若只是上传命中次数，应改名并用于统计，而不是安全删除。

### 4.4 管理员手动重建失败应返回失败

现状：总榜维护内部会捕获运行时异常并只记日志，管理员 HTTP 入口可能仍返回 200。

建议：

- 定时任务入口允许吞异常并记录；
- 管理员显式操作必须向上抛业务异常；
- 测试 Redis/MySQL 失败时 HTTP 状态和错误码。

## 5. 搜索演进

### 阶段 1：继续使用 MySQL，但完成测量

- 构造接近目标规模的数据；
- 使用慢查询日志和 `EXPLAIN ANALYZE`；
- 检查组合筛选、排序和深分页；
- 对搜索结果定义基础相关性规则。

### 阶段 2：全文检索

当 `%LIKE%` 无法满足数据量和体验时，再选择：

- MySQL 全文索引：组件少，能力有限；
- Elasticsearch/OpenSearch：中文分词、倒排索引、相关性、高亮和聚合更强，但有双写一致性和运维成本。

### 阶段 3：语义能力

只有在明确需求后再增加：

- 文档文本抽取；
- Embedding；
- 向量索引；
- 关键词与向量混合检索；
- 权限过滤和审核状态同步。

不能因为项目名称有“智能”就直接引入大模型。

## 6. 文件存储演进

### 当前边界

- 文件保存在单机本地目录；
- 多实例部署时其他实例不一定能读到同一文件；
- 扩展名白名单不能确认真实文件内容；
- 没有断点续传和大文件分片。

### 演进路线

1. 增加文件魔数/MIME 内容识别；
2. 对压缩包限制展开大小、文件数和嵌套层数；
3. 引入杀毒或内容安全扫描；
4. 迁移到 MinIO/OSS，`storage_type` 和 `storage_path` 已留扩展字段；
5. 下载改为服务端鉴权后签发短期对象存储 URL；
6. 大文件需要分片上传、分片哈希和合并幂等。

## 7. 排行榜演进

### 7.1 精确自然周期

当前 Key 是固定 `daily/weekly/monthly`，写入会续期，并非自然日、周、月切桶。

改进 Key：

```text
crp:rank:resource:hot:day:20260728
crp:rank:resource:hot:week:2026-W31
crp:rank:resource:hot:month:202607
```

查询只读当前桶或显式历史桶，TTL 用于保留历史，不再承担“周期切换”。

### 7.2 时间衰减

当前公式是累计：

```text
download * 5 + favorite * 3 + view * 1
```

但浏览事件尚未落地，也没有时间衰减。可引入：

- 最近行为窗口；
- 指数衰减；
- 新资料冷启动基础分；
- 反作弊权重。

公式必须能解释并通过数据验证，不能为了复杂而复杂。

### 7.3 运维可观测性

- Micrometer 指标：任务耗时、批次大小、失败次数、待同步 field 数；
- 告警：同步连续失败、`syncing` 批次长时间未确认、排行榜重建失败；
- 管理员重建任务 ID 和执行结果；
- 历史任务记录而非仅进程内最后一次快照。

## 8. 测试与性能演进

### 当前可以证明

- 有 31 个 Java 测试类和 31 个前端测试文件；
- 本轮 Maven 全量执行 167 项：158 项通过、0 项断言失败，9 项 MySQL 审核集成测试因本机 `localhost:3306` 未启动而连接错误；当前环境不能证明全量通过；
- 本轮前端因 `vitest`、`vue-tsc` 命令不可用，未能执行单元测试和构建；
- 覆盖 Controller、Service、Mapper/数据库集成和任务逻辑；
- 文件、下载、收藏、审核和排行榜均有专项测试。

### 当前不能证明

- 生产容量和 QPS；
- Redis/网络真实故障下的行为；
- 当前提交在具备 MySQL 集成环境和完整前端依赖时的全量绿灯；
- 多实例竞争；
- 跨日/周/月榜单切换；
- 文件大规模上传和磁盘压力；
- 真实数据库数据量下的搜索性能。

### 建议验证顺序

1. Testcontainers 启动真实 MySQL 和 Redis；
2. 下载 Lua、锁、宕机恢复和幂等集成测试；
3. 资料重复提交和收藏并发测试；
4. 自然周期榜跨边界测试；
5. 搜索数据规模与执行计划测试；
6. 最后再做接口压测和容量报告。

压测报告至少记录硬件、JVM、数据库/Redis配置、数据量、并发模型、P50/P95/P99、错误率和瓶颈，不能只给一个平均 QPS。

## 9. 分阶段实施优先级

### P0：面试前先把口径说准

- 明确原生 MyBatis，不是 MyBatis-Plus；
- 明确 MySQL 搜索，不是语义检索；
- 明确当前榜单不是自然周期；
- 明确下载成功计数时点；
- 明确没有生产压测数据。

### P1：安全和正确性

- 用户级 Token 失效；
- 下载计数时点；
- 可信代理 IP；
- 下载去重 + Hash 增量 Lua 原子化；
- 管理员重建失败传播。

### P2：并发和数据语义

- 资料提交幂等；
- 修正 `ref_count`；
- 空收藏缓存；
- 真实 Redis/MySQL 故障测试。

### P3：体验和扩展

- 精确自然周期榜；
- 全文检索；
- 对象存储；
- 可观测性与压测；
- 容器化和 CI/CD。

## 10. 面试回答模板

被问“为什么没做某项优化”时：

> 当前阶段先保证主业务闭环和关键一致性，所以采用了 X。它在当前教学规模下依赖少、容易验证，但边界是 Y。如果数据量或部署形态达到 Z，我会先用指标确认瓶颈，再按 A、B、C 的顺序演进，而不是一开始就引入复杂组件。

这个回答要替换成具体内容。例如搜索可以说 MySQL `LIKE`、前导模糊索引受限、数据量增长后用执行计划验证，再评估 Elasticsearch。
