# 项目背景与价值表达

## 1. 一句话定位

校园资料共享与智能检索平台是一个围绕“资料上传、审核发布、检索下载、收藏排行”闭环构建的 Java 后端项目，重点解决校园资料分散、重复存储、质量不可控、检索困难和下载滥用问题。

当前“智能检索”主要体现为多条件检索、排序、热门搜索词和热门资料推荐，不包含 Elasticsearch、向量检索或大模型语义能力。

## 2. 项目背景

校园资料通常分散在班级群、个人网盘和临时聊天记录中，存在五类问题：

1. **资料分散**：新同学难以知道资料在哪里，链接也可能失效。
2. **重复存储**：同一份课件或真题被多人重复上传，占用空间。
3. **质量不可控**：没有审核和下架机制，错误、侵权或低质量资料可能直接传播。
4. **检索效率低**：只能依赖文件名或人工翻找，缺少课程、类型、标签等结构化条件。
5. **访问容易被滥用**：下载接口如果只暴露文件路径，容易被越权、重放或高频刷取。

项目不是把这些问题拆成互不相关的 CRUD，而是形成一条有状态、有权限、有审计、有派生数据的业务链。

## 3. 项目价值

### 对学生用户

- 通过课程、分类、资料类型、标签和关键词检索公开资料；
- 相同内容可复用物理文件，减少重复上传等待；
- 查看自己的上传、收藏和下载记录；
- 只消费审核通过的资料，降低无效内容干扰。

### 对管理员

- 通过明确状态机完成审核通过、拒绝和下架；
- 保留每次操作的前后状态、原因和操作人；
- 只能读取与待审核资料绑定的文件，不能把审核入口变成任意文件下载入口；
- 通过排行榜重建和任务状态了解派生数据维护情况。

### 对系统

- MySQL 保存用户、资料、文件、收藏、下载和审核等权威业务数据；
- Redis 承担黑名单、去重缓存、限流、一次性票据、排行榜和增量统计；
- 数据库唯一索引、条件更新和事务处理并发重复操作；
- Redis 异常按业务重要性选择失败关闭、降级 MySQL 或跳过派生统计。

## 4. 为什么不是普通 CRUD

普通 CRUD 只回答“如何增删改查一张表”。本项目还需要回答：

| 复杂点 | 本项目处理方式 |
| --- | --- |
| 资料什么时候可以公开 | `PENDING_REVIEW -> APPROVED/REJECTED -> OFFLINE` 状态机 |
| 两个管理员同时审核怎么办 | SQL 携带旧状态条件，只有一个请求能更新成功 |
| 文件相同但用户不同怎么办 | 物理文件全局去重，用户引用权限单独落表 |
| 重复收藏怎么办 | `(user_id, resource_id)` 唯一索引 + 状态条件更新 + 幂等返回 |
| 高频下载如何防刷 | 用户/IP 双维度 ZSet 滑动窗口 + Lua 原子脚本 |
| 文件 URL 被转发怎么办 | 60 秒随机一次性票据，摘要入 Redis，取流前再次校验状态与归属 |
| 下载量高频更新怎么办 | Redis Hash 聚合增量，定时批量同步 MySQL |
| 同步任务重试会不会重复加数 | UUID 批次 + MySQL 唯一幂等明细 |
| Redis 排行榜故障怎么办 | MySQL `hot_score` 快照兜底，总榜可从 MySQL 重建 |
| 事务提交后 Redis 写失败怎么办 | 权威数据以 MySQL 为准，Redis 作为缓存或可重建派生数据降级 |

这些问题覆盖了状态机、权限、并发、幂等、缓存一致性、最终一致性和故障降级，是项目的核心面试价值。

## 5. 不同时间长度的项目介绍

### 5.1 30 秒版本

> 我做的是一个校园资料共享与检索平台，后端使用 Java 17、Spring Boot、MyBatis、MySQL 和 Redis。用户可以上传文件并创建资料，管理员审核通过后，资料才能被搜索、下载和收藏。项目里我重点处理了文件 MD5 去重、JWT 鉴权、审核状态机、Redis 滑动窗口限流、一次性下载票据、ZSet 排行榜，以及下载量从 Redis 批量同步 MySQL 的幂等和最终一致性问题，所以它不只是简单的增删改查。

### 5.2 1 分钟版本

> 这个项目解决校园资料散落在群聊和网盘中、重复存储、质量不可控和查找困难的问题。主流程是用户注册登录后上传文件，系统按 MD5 和文件大小去重，同时为当前用户建立文件引用权限；用户再填写课程、分类和标签创建待审核资料。管理员只能把待审核资料通过或拒绝，通过后才能公开搜索、下载和收藏，已通过资料还可以被下架。
>
> 技术上，Spring Boot 负责 Web 分层、校验、异常处理、拦截器、事务和定时任务；MyBatis XML 编写动态 SQL，并对白名单排序防止 SQL 注入；MySQL 保存权威数据，用唯一索引和条件更新处理并发；Redis 用于 JWT 黑名单、MD5 缓存、收藏集合、下载限流、一次性票据、排行榜和下载增量。下载增量不是每次都直接更新 MySQL，而是先聚合到 Redis，再通过带分布式锁和批次幂等记录的任务同步，降低热点行写压力。

### 5.3 3 分钟版本

> 项目背景是校园资料长期分散在聊天群和个人网盘。仅做一个资料表的 CRUD 不能解决三个核心问题：相同文件被重复存储、未审核内容直接公开、下载和统计容易被刷。因此我把系统拆成认证、文件、资料、审核、搜索、下载、收藏和排行榜模块。
>
> 认证使用 JWT。登录成功后服务端签发带用户 ID、角色和 jti 的 Token，拦截器解析后写入 ThreadLocal，并在请求结束清理。退出登录把 jti 放进 Redis 黑名单，TTL 等于 Token 剩余时间。管理员身份来自 JWT 上下文，不接收前端传来的角色参数。
>
> 文件上传时先校验大小和扩展名，再计算 MD5。物理文件按 `MD5 + size` 唯一去重，但为了防止用户猜到别人的 fileId 后直接创建资料，我又增加了 `user_file_authorization`，把“文件存在”和“当前用户有权引用”分开。文件 IO 放在数据库事务外，入库失败时做删除补偿，避免长事务占用连接。
>
> 资料创建后状态是待审核。审核通过、拒绝和下架都用带旧状态条件的 SQL，防止两个管理员并发操作；资料状态更新与审核流水在同一 MySQL 事务中，排行榜更新放在事务提交后，避免数据库回滚但 Redis 已经变化。
>
> 下载是两段式流程。第一步同时做用户和 IP 的 Redis ZSet 滑动窗口限流，写下载记录并签发 60 秒一次性随机票据；第二步原子消费票据，再校验记录归属、资料仍然通过审核、文件关系没有变化，最后才返回文件流。十分钟内同用户重复下载同一资料可以继续下载，但不重复计数。
>
> 下载量先累加到 Redis Hash，再由每分钟任务同步 MySQL。任务使用 Redisson 看门狗锁避免多实例并发同步，用 UUID 隔离批次，并在 MySQL 中通过 `(batch_id, resource_id)` 唯一键防止“数据库已提交、Redis 确认失败”后的重复累加。排行榜用 ZSet 维护日、周、月、总榜；Redis 不可用时资料榜降级到 MySQL 热度快照，总榜丢失时可以从 MySQL 重建。
>
> 当前项目仍有明确边界：搜索是 MySQL `LIKE` 和结构化筛选，不是语义检索；文件是本地存储；没有真实生产压测数据。这些我会作为下一阶段演进，而不会在面试里当成已经完成。

## 6. 简历表达示例

以下内容可以按简历版面选 3 到 4 条，不建议全部堆入：

- 基于 Java 17、Spring Boot 3.5、MyBatis、MySQL 与 Redis 实现校园资料上传、审核、检索、下载、收藏和排行榜闭环，当前仓库包含 28 个 REST 接口方法与 9 张业务表。
- 设计文件 `MD5 + size` 唯一去重和用户级文件引用授权，支持物理文件复用，并阻止用户通过猜测 `fileId` 越权创建资料。
- 使用 MySQL 事务、唯一索引和带旧状态的条件更新实现审核状态机与收藏幂等，保证资料状态、审计流水和收藏计数一致。
- 使用 Redis ZSet + Lua 实现用户/IP 双维度滑动窗口限流，使用 60 秒一次性下载票据和取流前复核降低重放、越权和已下架资料继续下载的风险。
- 设计 Redis Hash 下载增量、Redisson 看门狗锁、UUID 隔离批次和 MySQL 唯一幂等栅栏，实现下载量批量落库与失败重试。
- 使用 Redis ZSet 维护多周期热门资料和搜索词榜单，Redis 异常时通过 MySQL 热度快照降级，并支持总榜原子重建。
- 通过 Controller、Service、Mapper 与数据库集成测试覆盖核心链路；当前已有 Surefire 报告记录 124 个测试全部通过。

## 8. 面试表达公式

每个技术点优先按下面顺序回答：

```text
业务问题
→ 为什么朴素方案不够
→ 当前方案和真实调用链
→ 并发/异常时如何处理
→ 方案的代价
→ 下一步如何优化
```

例如不要只说“我用了 Redis ZSet”，而要说“热门资料需要持续按分数排序，ZSet 能直接按 score 取 Top N；但 Redis 是派生数据，所以查询失败时降级 MySQL 快照，总榜缺失时从 MySQL 重建”。
